# Refactoring plan

The toolkit grew feature by feature in three weeks. Everything works, but the same idea is now written several times and the site ships more than it needs. This is the plan to make it **lighter, simpler and safer to change** without changing what people see. Measured on `develop` on **2026-11-16**.

Each phase is one or more small pull requests; a ready prompt for the AI assistant is at the end of each phase.

## Rules for the whole refactor

1. **Behaviour does not change.** A refactor pull request changes no pixel and no generated byte, unless it says so in its title.
2. **The safety net comes first** (phase 0). No structural change before the generated banners are pinned by tests.
3. **One idea per pull request**, reviewable in ten minutes. No "while I was there".
4. **Generated banners stay byte-identical** to the golden files, or the pull request shows the diff and says why.
5. **Old zips keep opening.** Every zip format made so far has a fixture in the tests.
6. Measure before and after: script size (gzip), `dist/` size, runtime size. Write the numbers into the pull request.

## Phase 0: safety net (do this first)

**Goal:** a change that breaks a banner fails a check instead of reaching ad sales.

1. **Vitest** in `packages/templates`: one fixture config per format (articles desktop with and without ad, articles mobile, slider desktop and mobile, picture loop fixed and responsive, responsive banner video and pictures, header bar). Render each and compare with a stored golden `index.html`.
2. **Unit tests for the rules that already broke**: picture sizes (desktop never 48, mobile 48 unless an own picture, uploaded `pic-*` names), `validate`, colour contrast (`readableOn`, brand text rule), zip name stamps, fade timeline (`frameTimeline`, never a moment without a solid picture).
3. **Zip round trip** in the app (Vitest + jsdom): build a zip from each fixture, open it again, expect the same draft. Add one real old Swiper zip per legacy importer (made-up content, no customer material).
4. **ESLint + Prettier** with the current style (long lines are the house style: set the print width to match, do not reformat the world). One format-only commit, clearly labelled.
5. **GitHub Actions on every pull request:** typecheck (all workspaces), tests, build, runtime size budget, `yarn docs:check`, and a **bundle budget** (fails when the first-load script grows above the agreed number).
6. **Publish on merge to `develop`**: the same steps as [DEPLOY.md](DEPLOY.md) in a workflow using the built-in `GITHUB_TOKEN`. No personal token in a chat any more. (An earlier custom Pages workflow failed; push to the `gh-pages` branch from the workflow instead of using the Pages deploy action.)

**Done when:** a pull request that changes one character of a banner template goes red; a merge to `develop` is live two minutes later without anyone running a command.

**Model:** Sonnet. Closes #5, #6.

## Phase 2: one banner model (the real simplification)

**Goal:** adding a banner type is one folder, not eight files.

Today each kind (`banner`, `header`, `slider`, `frames`, `responsive`) has its own draft shape, its own zip build and import, its own branch in `storage.ts`, and `App.tsx` tries the importers one after another.

1. **One draft shape for all kinds:** `{ kind, config, files: Record<string, FileEntry> }`. The articles banner's `headerFile`, `adFile`, `logoFile`, `articleFiles` become entries in `files` (the config already holds the names). The header bar's `picture` too.
2. **One zip module:** `buildZip(draft)` writes `index.html` plus the files the config refers to; `importZip(file)` reads the embedded settings and **dispatches on `kind`** (old zips without `kind` are recognised once, in one place). Every kind uses the id `ol-banner` (the header bar's `ol-header` stays readable).
3. **One storage path:** `saveWork` and `loadWork` lose their five branches. Videos stay out of `localStorage` through one rule ("files above N bytes are not kept"), not a special case.
4. **A format registry:** `apps/generator/src/formats/<id>/` holds `defaults.ts`, `Editor.tsx`, `io.ts` (what to render, which files belong), and one `index.ts` registers `{ id, kind, icon, texts, newDraft, Editor, render }`. `App.tsx`, `route.ts`, `Home`, `ContentMarketingHome` and `ContinueCard` read the registry instead of repeating lists.
5. **Legacy importers** (`legacy.ts`, `legacyExtra.ts`, `legacySlider.ts`, about 430 lines) move behind one lazy import: only a person who uploads an old zip downloads them.

**Done when:** the round-trip tests from phase 0 pass unchanged; `App.tsx` has no `kind ===` chains; a sixth banner type can be added without editing `App.tsx`, `storage.ts` or `route.ts`.

**Model:** Opus for the design of step 1 and 4 (one short design note first), Sonnet for the mechanical moves.

## Phase 3: one editor frame

**Goal:** the five editors share their frame and differ only in their form.

1. `ToolShell` (used by the two newest editors) becomes the frame of all five: back button, name, version switch, weight pill, "to fix" list, download, preview column. `BannerEditor`, `SliderEditor` and `HeaderBarEditor` lose about 100 lines each.
2. Shared parts that are now copied: the picture upload button with its hidden input and spinner (written again in every editor), `reportOptimised`, the weight calculation, the `work()` busy helper.
3. `SliderEditor.tsx` (466 lines) splits into the form sections it already has.
4. A file over 300 lines is a signal to split, not a rule.

**Done when:** each editor file holds only its own fields; a visual check of all five editors at 375 px and 1440 px, light and dark, shows no difference.

**Model:** Sonnet.

## Phase 4: app shell and routing

1. A small **route table** replaces the separate `useState` values and effects for the address in `App.tsx`: one `useRoute()` hook that reads and writes `location.search` (`section`, `tool`, `tab`, `make`, `topic`, `step`, `lang`). No router library is needed.
2. `nav` and the page list come from one place (the registry of phase 2 for banners, a small table for tools).
3. Custom window events (`ol-downloaded`, `ol-reveal`) become a tiny typed event helper or context.

**Model:** Sonnet.

## Phase 5: templates

1. **One module for picture sizes** in `packages/templates` (`pictures.ts`): `desktopPicture(url)`, `mobilePicture(article)`, `withPictureSize`, `OWN_PICTURE`. Templates, the form, the converter and the bookmark all use it. The numbers 48 and 54 appear once.
2. A small `html` helper for the long string concatenations (escaping by default), so a template reads top to bottom.
3. Shared CSS pieces (header, reset, focus ring) defined once and reused by the article templates.
4. The settings block in `index.html` (`ol-banner`) stays: it is what lets a zip open again. Write it minified and without default values to keep it short.

**Model:** Sonnet, with the golden tests as the guard. Any byte that changes in a golden file is listed in the pull request.

## What not to do

- Do not add a router, a state library or a form library. The app's state is small; the problem is repetition, not missing tools.
- Do not rewrite the banner runtime. It is small, tested by hand in real campaigns and under budget.
- Do not rename folders (`apps/generator` to `apps/web`) during the refactor: it makes every diff unreadable. Do it last, alone, or never.
- Do not mix a refactor with a feature in one pull request.
